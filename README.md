# Telegram-система агентів команди

Архітектура: Telegram → оркестратор (Claude) → агенти-виконавці
(задачі, деплой, багфікси, презентації, дизайн, стендап, ідеї) +
окремий health-check процес. Кожен агент (крім задач/презентацій) має
**власну ідентичність у Telegram** — окремого бота, що постить під
своїм ім'ям, а не все через одного диспетчера (див. "Мульти-бот
система" нижче).

```
Telegram → bot.py ─┬─ @Dispatcherqq_bot (диспетчер: задачі, презентації, статус)
                    ├─ @bagfixer_bot (сповіщення багфікс-агента + кнопки)
                    ├─ @ddeeployy_bot (сповіщення деплой-агента + кнопки)
                    ├─ @dessiignn_bot (/дизайн — HTML-мокапи)
                    ├─ @standuppp_bot (/стендап — щоденне зведення)
                    └─ @ideeaagentik_bot (/ідея_* — щотижневі ідеї)

orchestrator.classify() ─┬─ storage.py (tasks.json)
                          ├─ presentation.py (/презентація)
                          ├─ design.py (/дизайн)
                          ├─ standup.py (/стендап)
                          ├─ ideas_agent.py + ideas_storage.py (/ідея_*)
                          ├─ agents/deploy_agent.py (крон, GitHub Actions)
                          └─ agents/bugfix_agent.py (issue → PR, GitHub Actions)

watchdog.py (окремо, cron) — пінгує bot.py, перезапускає, шле алерти
```

## Структура

- `bot.py` — точка входу: усі 6 ботів (Bot+Dispatcher пари в одному процесі), команди, теги `@дизайн`/`@багфікс`/`@деплой`, обробник помилок, heartbeat, callback-кнопки, `/статус_агентів`
- `orchestrator.py` — Claude визначає намір вільного тексту (задача / список / чат)
- `storage.py` — задачі команди, JSON-файл `tasks.json` (поле `agent`, якщо задачу додано через тег)
- `presentation.py` — генерація pptx-звіту для `/презентація`
- `design.py` — генерація HTML-мокапу для `/дизайн` (Groq, фолбек — Claude)
- `pitch.py` — генерація pptx-пітчу ідеї для `/дизайн_презентація` (Gemini, фолбек — Claude)
- `standup.py` — щоденне зведення для `/стендап` (задачі + відкриті PR)
- `ideas_agent.py` — генерація ідей для `/ідея_продукт`/`/ідея_контент` (Gemini, фолбек — Claude)
- `ideas_storage.py` — збережені ідеї, JSON-файл `ideas.json`
- `PRODUCT.md` — продуктовий/дизайн-бриф (навігація, дизайн-токени, функціонал, відомі баги, стек), читають `design.py`/`ideas_agent.py`/`pitch.py` (не хардкод у промптах)
- `agents/common.py` — спільне: Telegram-алерти, GitHub REST helpers (merge/close PR, issue, статус/запуск workflow), `call_groq`/`call_gemini` (безкоштовні API), `load_product_description()` — і для крон-агентів, і для bot.py
- `agents/deploy_agent.py` — деплой-агент (крок 2), підкоманди autofix/test/open-pr/merge-pr
- `agents/bugfix_agent.py` — багфікс-агент (крок 3), підкоманди propose/test/open-pr
- `watchdog.py` — health-check процес (крок 5)
- `.github/workflows/` — крони й тригери для деплой-, багфікс-агентів і CI
- `.github/scripts/telegram_notify.sh` — curl-сповіщення в Telegram прямо з кроків workflow (текст + кнопки підтвердження)
- `tests/` — pytest-тести (потрібні, щоб деплой-агенту й CI було що ганяти)

## Встановлення

```bash
pip install -r requirements.txt --break-system-packages
cp env.example .env
# відкрийте .env і впишіть TELEGRAM_BOT_TOKEN, ANTHROPIC_API_KEY, ALLOWED_USER_IDS
# опційно: GROQ_API_KEY/GEMINI_API_KEY — див. "Крок 7" нижче, щоб дизайн-/
# ідея-/пітч-агент йшли через безкоштовні тарифи, а не завжди через Claude
python bot.py
```

Для локального лінту/тестів (не обов'язково для проду — CI ставить їх сам):

```bash
pip install pytest ruff --break-system-packages
ruff check .
pytest -q
```

## Налаштування репозиторію на GitHub (потрібне для кроків 2-3)

1. Запуште цей репозиторій на GitHub.
2. Settings → Secrets and variables → Actions → додайте:
   `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`.
3. Settings → Actions → General → "Workflow permissions" → увімкніть
   *Read and write permissions* і *Allow GitHub Actions to create and
   approve pull requests* — інакше `deploy_agent.py`/`bugfix_agent.py`
   не зможуть пушити гілки й відкривати PR через `GITHUB_TOKEN`.
4. Створіть лейбл `bug` у репозиторії (Issues → Labels), якщо його
   нема — на нього зав'язаний тригер багфікс-агента.
5. У `.env` бота (не в GitHub secrets — це для процесу на вашому
   хості) заповніть `GITHUB_TOKEN`/`GITHUB_REPOSITORY` з правами
   `Issues: write`, `Pull requests: write`, `Actions: read+write`
   (write — для тега `@деплой`, що запускає workflow позачергово) —
   інакше кнопки "Затвердити"/"Відхилити" й `/статус_агентів` не
   працюватимуть (див. "Доповнення: усе керування — з Telegram" нижче).

## Крок 1 — MVP-каркас (задачі команди)

Було в стартовому каркасі: `bot.py`, `orchestrator.py`, `storage.py`.
Перевірено: `python3 -m py_compile` на всіх файлах, повний прогін
`pytest` і `ruff check .` — чисто. Синтетичних тестів у каркасі не
було, тож додано `tests/test_storage.py`, аби деплой-агенту й CI (крок
2-3) було що реально ганяти.

**Як перевірити:** `pip install -r requirements.txt`, заповнити `.env`,
`python bot.py`, у Telegram — `/задача`, `/задачі`, `/done <id>`.

## Крок 2 — Деплой-агент

`agents/deploy_agent.py` + `.github/workflows/deploy-agent.yml` (крон
раз на годину, і `workflow_dispatch` для ручного запуску).

Скрипт розбитий на підкоманди — кожна є окремим кроком workflow, щоб
після кожного кроку одразу летіло сповіщення в Telegram (через
`.github/scripts/telegram_notify.sh`, curl до Bot API), навіть якщо
наступний крок впаде:

1. `autofix` — `ruff check --fix .`, виводить `has_changes`
2. `test` — `pytest`, виводить `passed`
3. `open-pr` — Claude оцінює diff на "тривіальність", коммітить,
   пушить, відкриває PR; виводить `pr_number`/`pr_url`/`trivial`/`reason`
4. `merge-pr <pr_number>` — squash-мердж, лише якщо `trivial=true`

**Лише тривіальні (форматування/лінт/залежності) і покриті тестами
зміни мерджаться автоматично** — це єдиний агент системи з таким
правом. В усіх інших випадках (і якщо автомердж тривіального PR
раптом не вдався, напр. через branch protection) workflow сам шле в
Telegram повідомлення з кнопками "✅ Затвердити і замерджити" /
"❌ Відхилити" — натискання обробляє `bot.py` (див. розділ нижче).

**Як перевірити:**
- Локально без реального GitHub: `python agents/deploy_agent.py autofix`
  і `python agents/deploy_agent.py test` (перевіряють логіку без push/PR;
  `open-pr`/`merge-pr` вимагають git remote + `gh auth`).
- В GitHub Actions: вкладка Actions → "Deploy agent" → "Run workflow" —
  і дивитись прогрес прямо в Telegram-чаті, не в логах Actions.

## Крок 3 — Багфікс-агент

`agents/bugfix_agent.py` (підкоманди `propose`/`test`/`open-pr`, той
самий принцип — крок workflow = сповіщення в Telegram) +
`.github/workflows/bugfix-agent.yml` (тригер: GitHub issue з лейблом
`bug`) + `.github/workflows/ci.yml` (тести/лінт на кожен push/PR).

Джерела помилок (рішення: без Sentry, напряму з логів):
1. **CI на main впав** → `ci.yml` сам відкриває issue з лейблом `bug`
   і посиланням на лог провалу (з дедупом — не плодить дублікати) і
   одразу шле в Telegram повідомлення з посиланням на issue.
2. **Виняток у проді** → глобальний `@dp.error()` у `bot.py` пише
   повний traceback у `errors.log` і, якщо на хості налаштовані
   `GITHUB_TOKEN`/`GITHUB_REPOSITORY`, відкриває issue з лейблом `bug`
   напряму через GitHub REST API (без залежності від `gh` CLI на проді).

У обох випадках issue з лейблом `bug` тригерить `bugfix-agent.yml`:
Claude отримує текст issue + весь `.py`-код репозиторію, пропонує фікс
одного файлу (`propose`), скрипт застосовує його й ганяє тести
(`test`). Тести червоні — зміни відкидаються (`git checkout -- .`), в
issue лишається коментар для людини. Тести зелені — відкривається PR
("Fixes #N", крок `open-pr`). **Багфікс-агент ніколи не мерджить сам**
(навіть тривіальні фікси) — workflow завжди шле кнопки
"Затвердити"/"Відхилити" в Telegram, за рішенням команди.

**Як перевірити:**
- Локально: `python agents/bugfix_agent.py propose <номер-issue>`
  (застосує фікс у робочу директорію, не пушить і не створює PR).
- Наживо: створіть issue з лейблом `bug` на GitHub — запуститься workflow,
  прогрес побачите в Telegram, а не в логах Actions.
- Прод-помилки: тимчасово зробіть так, щоб хендлер бота кинув виняток
  (напр. `/задача` без обробки якогось едж-кейсу) — перевірте, що
  з'явився запис в `errors.log` і (за наявності токена) нова issue.

## Крок 4 — Презентації

Команда `/презентація` (`presentation.py`, бібліотека `python-pptx`).

`/презентація` — звіт за 7 днів (дефолт), `/презентація 30` — за 30
днів, `/презентація all` — за весь час. Дані ті самі, що й у
`/задачі` (той самий `tasks.json`, нового сховища не додано). Слайди:
титульний, підсумок (закрито/відкрито/разом), список закритих задач,
список відкритих.

**Як перевірити:** додайте кілька задач через `/задача`, закрийте
одну через `/done`, викличте `/презентація` — бот надішле `report.pptx`
у чат. Локально без Telegram: `python -c "from presentation import
build_report; print(build_report(days=30))"`.

## Крок 5 — Health-check / watchdog

`watchdog.py` — окремий процес, **не агент** (немає доступу до Claude
API, не редагує код, не відкриває PR) — свідомо, щоб право
"перезапускати все" не поєднувалось із правом самомодифікації.

`bot.py` раз на 60с оновлює `heartbeat.txt` і при старті пише свій pid
у `bot.pid`. `watchdog.py` перевіряє: чи процес з `bot.pid` живий, і чи
`heartbeat.txt` не старший за 180с (3x інтервал з запасом). Якщо ні —
перезапускає `bot.py` (`subprocess.Popen`) і шле алерт у
`TELEGRAM_ALERT_CHAT_ID` — тим самим `notify_telegram` і в той самий
чат, що й python-сповіщення з інших частин системи (стиль/чат
узгоджені з доповненням нижче). Деплой/багфікс-агенти сюди не входять
— це не довгоживучі процеси, а GitHub Actions джоби за розкладом/подією.

При кожному запуску (навіть якщо все ок) `watchdog.py` оновлює й
власний `watchdog_heartbeat.txt` — за ним `/статус_агентів` у `bot.py`
визначає, чи системний cron взагалі викликає watchdog (окремо від
питання "чи живий бот").

Запуск (рекомендовано — системний cron, раз на 5 хв):
```
*/5 * * * * cd /path/to/repo && /path/to/venv/bin/python watchdog.py
```
або в режимі фонового циклу: `python watchdog.py --loop --interval 300`.

**Як перевірити:** запустіть `python bot.py` в одному терміналі,
переконайтесь, що з'явились `bot.pid`/`heartbeat.txt`; `kill <pid>` з
`bot.pid` і одразу `python watchdog.py` — має надіслати алерт і
перезапустити бота. Без реального `TELEGRAM_ALERT_CHAT_ID` алерт просто
друкується в консоль (`[telegram alert skipped...]`), бот не падає.

## Доповнення: усе керування — з Telegram

Мета: людина сидить тільки в Telegram — бачить прогрес агентів,
тисне кнопку "затвердити" чи отримує готовий pptx, і не заходить на
GitHub (хіба що сама захоче подивитись деталі).

1. **Покроковий прогрес деплой/багфікс-агентів.** Кожен крок
   `deploy-agent.yml`/`bugfix-agent.yml` (почав перевірку → тести →
   PR відкрито → мердж/потрібне підтвердження, або аварійне
   завершення) одразу шле повідомлення в Telegram через
   `.github/scripts/telegram_notify.sh` — curl до Bot API прямо з
   workflow, а не з python. Свідомий вибір: якщо сам python-скрипт
   впаде посеред кроку, повідомлення про попередні кроки вже пішли, і
   є окремий `if: failure()` крок в кінці job'а, який теж шле алерт —
   тиша в Telegram неможлива навіть при незапланованому падінні.
   Дані для повідомлень (номер PR, причина від Claude тощо) передаються
   з python-підкоманд через `$GITHUB_OUTPUT`, а в bash-крок — через
   `env:`, а не інлайном у `${{ }}` всередині `run:` — це навмисно,
   щоб вміст, згенерований Claude (текст, який теоретично може містити
   спецсимволи), не потрапляв напряму в тіло shell-скрипта.
2. **Кнопки "Затвердити"/"Відхилити".** Коли потрібне ручне
   підтвердження, `telegram_notify.sh approve` шле повідомлення з
   `inline_keyboard` (той самий Bot API `sendMessage`, просто з
   `reply_markup`), `callback_data` — `pr:approve:<N>` / `pr:reject:<N>`.
   Натискання ловить `bot.py` (`@dp.callback_query`, єдиний процес, що
   слухає Telegram-апдейти) і мерджить/закриває PR через GitHub REST
   API (`agents.common.merge_pr`/`close_pr`, urllib — без PyGithub чи
   httpx, щоб не тягнути нові важкі залежності). Потребує на боті
   `GITHUB_TOKEN` з правом `Pull requests: write` (див. `env.example`).
   Перевірку прав (`ALLOWED_USER_IDS`) зроблено і для кнопок, не лише
   для команд.
3. **Презентація одразу у чат.** `/презентація` й раніше завершувалась
   `message.answer_document(...)` (аналог `bot.send_document` під
   капотом aiogram) — файл летить прямо в чат, посилання чи шлях на
   диску користувачу не показуються. Змін не знадобилось.
4. **Узгоджений формат сповіщень.** Watchdog і раніше слав алерти в
   `TELEGRAM_ALERT_CHAT_ID` — той самий chat id, що тепер
   використовують і curl-кроки workflow (той самий repo secret).
   Емодзі-конвенція наскрізна: 🚀 старт/успіх, 🧪 тести, 📬 PR відкрито,
   ✅ мердж/ок, ❌ відхилено/не пройшло, ⚠️ треба увага, 🔥 аварія,
   🐕 watchdog.
5. **`/статус_агентів`** — читає (без заходу на GitHub з боку людини):
   останній запуск деплой-агента (`get_last_workflow_run`, GitHub
   Actions API), кількість відкритих PR від деплой/багфікс-агентів
   (`list_open_agent_prs`, за префіксом гілки), і чи `watchdog.py`
   взагалі викликається системним croном (`watchdog_heartbeat.txt`).

**Як перевірити:**
- `bash .github/scripts/telegram_notify.sh text "тест"` локально з
  реальними `TELEGRAM_BOT_TOKEN`/`TELEGRAM_ALERT_CHAT_ID` в env —
  прийде повідомлення в чат.
- Запустіть деплой-агент вручну (Actions → "Run workflow") і дивіться,
  як прогрес з'являється в Telegram кроками, а не одним фінальним
  повідомленням.
- Натисніть кнопку під повідомленням про підтвердження — переконайтесь,
  що PR на GitHub справді змерджений/закритий, а повідомлення в
  Telegram оновилось написом, хто натиснув.
- `/статус_агентів` у боті — має показати дані з GitHub, якщо
  `GITHUB_TOKEN`/`GITHUB_REPOSITORY` в `.env` бота налаштовані, і
  чесно написати "даних немає", якщо ні.

## Крок 6 — Ідея-агент

`ideas_agent.py` + `ideas_storage.py` + окремий бот `@ideeaagentik_bot`
(`TELEGRAM_IDEAS_BOT_TOKEN`). Генерує два типи ідей через Claude:

- **Продуктові** — конкретна фіча + одне речення, чому вона підвищить
  утримання/залучення. Команда `/ідея_продукт` — 5 штук.
- **Контентні** — короткі відео для Reels/TikTok (15-30с), конкретний
  формат (челендж, "до/після", "3 речі, які...", закадровий голос під
  екран застосунку), спільні під обидві платформи (не окремо TikTok
  vs Reels — рішення команди, простіше й менше шуму в чаті). Команда
  `/ідея_контент` — 5 штук.

Опис продукту винесено в `PRODUCT.md` (не хардкод у промпті) — щоб
міняти позиціонування без правок коду.

Кожна ідея приходить **окремим повідомленням** з кнопкою "💾 Зберегти"
і одразу зберігається в `ideas.json` зі статусом `new` (той самий
патерн, що `storage.py`: JSON-файл, `next_id`, статуси). Натискання
кнопки переводить у статус `saved`. `/ідеї_збережені` показує весь
список збережених.

**Розклад:** щотижня (за замовчуванням понеділок 10:00, `Europe/Kyiv`
— `IDEAS_DAY`/`IDEAS_TIME`/`IDEAS_TIMEZONE` в `.env`) бот сам, без
запиту, шле в груповий чат 3 продуктові + 3 контентні ідеї. На
відміну від щоденного стендапу (локальний час хоста), тут явно
використано `zoneinfo` (стандартна бібліотека Python 3.9+, без нової
залежності) — часовий пояс заданий точно, а не "як налаштовано на
Маку". Ліміту на ручні команди немає (рішення команди) — обмежена
лише авто-розсилка, 3+3 на тиждень.

**Як перевірити:**
- `/ідея_продукт`, `/ідея_контент` у Telegram — мають прийти по 5
  повідомлень від `@ideeaagentik_bot` з кнопками.
- Натисніть "Зберегти" на кількох — перевірте `/ідеї_збережені`.
- Локально без Telegram: `python -c "from ideas_agent import
  generate_product_ideas; print(generate_product_ideas(3))"`.
- Авто-розсилку без очікування вівторка можна перевірити, тимчасово
  виставивши `IDEAS_DAY`/`IDEAS_TIME` в `.env` на найближчу хвилину і
  перезапустивши бота.

## Крок 7 — Безкоштовні API замість Claude для дизайн-/ідея-/пітч-агента

Мотивація: Claude на кожен мокап/ідею/пітч (особливо з `xhigh`-thinking)
коштує помітно на масштабі команди. Багфікс-агент лишається **виключно
на Claude** (`agents/bugfix_agent.py`) — там ціна помилки найвища,
агент переписує реальний файл коду. Дизайн-, ідея- й пітч-агент —
творчі задачі з нижчою ціною просадки якості, тож для них додано
безкоштовні тарифи (каталог — [awesome-freellm-apis](https://github.com/open-free-llm-api/awesome-freellm-apis),
провайдер під кожен агент обраний під конкретну сильну сторону):

| Агент | Основний рушій | Модель | Фолбек |
|---|---|---|---|
| `design.py` (`/дизайн`) | Groq | `moonshotai/kimi-k2-instruct` (сильна для коду/HTML) | Claude |
| `ideas_agent.py` (`/ідея_*`) | Gemini | `gemini-3.6-flash` | Claude |
| `pitch.py` (`/дизайн_презентація`) | Gemini | `gemini-3.6-flash` | Claude |

Обидва — офіційні безкоштовні тарифи без картки (не reverse-engineered
обгортки): Groq 30 RPM/14400 RPD, Gemini Flash 15 RPM/1500 RPD.
Виклики — сирий `urllib` (як і GitHub/Telegram у `agents/common.py`,
`call_groq`/`call_gemini`), нових SDK-залежностей не додано.

**Фолбек автоматичний і мовчазний для користувача**: якщо
`GROQ_API_KEY`/`GEMINI_API_KEY` не задані в `.env`, чи безкоштовний
запит впав (ліміт, мережа, недоступність) — агент одразу й прозоро йде
через Claude (`ANTHROPIC_API_KEY`), як і раніше. Тобто без жодних змін
в `.env` уся система продовжує повністю працювати на Claude — безкоштовні
ключі лише додатково зменшують рахунок, коли вони налаштовані.

**Як увімкнути:** заповнити в `.env` `GROQ_API_KEY`
(console.groq.com/keys) і/або `GEMINI_API_KEY`
(aistudio.google.com/app/apikey) — обидва видаються за email, без
картки.

**Як перевірити:** тимчасово виставити свідомо неправильний
`GROQ_API_KEY`/`GEMINI_API_KEY` і викликати `/дизайн`/`/ідея_продукт` —
у консольному логі бота має з'явитись `[дизайн] Groq недоступний (...),
фолбек на Claude` (аналогічно для `[ідеї]`/`[пітч]`), а фіча все одно
відпрацює через Claude.

## Мульти-бот система і теги агентів

Кожен агент (крім задач/презентацій, які лишились у диспетчера)
отримав окрему ідентичність у Telegram — свій `TELEGRAM_*_BOT_TOKEN`,
своя пара `Bot`+`Dispatcher` у тому самому процесі `bot.py` (не окремі
скрипти — `watchdog.py` і далі стежить за одним процесом через один
`heartbeat.txt`/`bot.pid`). Якщо відповідний токен не заданий у
`.env` — команда/сповіщення того агента просто йде через основного
бота (graceful degradation, нічого не ламається).

**Теги в `/задача`** (і у вільному тексті) дають командам одразу
викликати агента, а не лише зберегти задачу:
- `/задача @дизайн <опис>` — одразу генерує HTML-мокап
- `/задача @багфікс <опис>` — одразу відкриває GitHub issue з лейблом
  `bug` (підхоплює вже готовий `bugfix-agent.yml`)
- `/задача @деплой <опис>` — запускає позачергову перевірку
  репозиторію (`agents.common.trigger_workflow_dispatch`), не чекаючи
  щогодинного cron

Задача при цьому все одно зберігається в `tasks.json` (без тега в
тексті), з полем `agent`, щоб `/статус_агентів` і `/стендап` могли
показати крос-агентне зведення — які задачі пішли якому агенту, і які
PR звідти ще чекають підтвердження, в одному повідомленні.

## Відомі обмеження (свідомо не рішали зараз)

- `watchdog.py` розрахований на один довгоживучий процес бота на
  одному хості (без HA/декількох реплік) — достатньо для команди 2-5 людей.
- Багфікс-агент за один прогін чіпає рівно один файл — свідоме
  спрощення, щоб не городити diff/patch-логіку; для складніших багів
  він чесно скаже "не можу визначити фікс" і лишить issue людині.
- Деплой-агент сканує й відкриває PR лише в цьому самому репозиторії
  (боті), не в репозиторії мобільного застосунку — за рішенням команди.
- Кнопки "Затвердити"/"Відхилити" довіряють будь-кому з `ALLOWED_USER_IDS` —
  немає окремої ролі "тільки читання"/"може мерджити"; для команди 2-5
  людей це прийнятно, але для більшої команди варто розділити ролі.
- Якщо повідомлення з кнопкою "протухло" (PR вже змерджено/закрито
  кимось напряму на GitHub), натискання поверне помилку від GitHub API
  замість тихого ігнорування — прийнятно для MVP, але не найкрасивіший UX.
